Section 02 · ChatGPT

General — 일반 설정

Workspace settings → General

워크스페이스의 “겉모습”과 “기본 정책”을 정하는 탭입니다. 이름과 로고처럼 사용자가 매일 보는 요소, 그리고 조직 전체에 일괄 적용되는 AI 사용 정책 모달이 여기에서 관리됩니다.

02.1Workspace name & image

이름 옆 연필(편집) 아이콘을 눌러 워크스페이스 이름·이미지를 바꿉니다. 저장하면 모든 멤버 화면에 즉시 반영됩니다.

02.2Workspace instructions

조직 차원에서 ChatGPT가 “어떻게 답해야 하는지” 알려주는 안내문입니다. 전사 톤앤매너, 피해야 할 표현, 공통 용어 등 조직 차원의 응답 지침을 설정합니다.

02.3Workspace policy modal

조직 AI 정책 모달을 켜면 30일마다, 그리고 정책 내용이 변경될 때 사용자에게 다시 표시됩니다. General의 정책 설정에서 관리합니다.

02.4Workspace & organization identifiers

워크스페이스 ID와 OpenAI 조직 ID(org-id)는 해당 화면에서 확인하고, 연동 대상 API가 요구하는 식별자를 사용합니다.

리소스 범위 확인
ChatGPT workspace와 API Platform organization은 같은 테넌트의 인증 연결을 공유할 수 있지만, 멤버십·권한·청구는 별도로 관리됩니다. ID가 같다고 가정하거나 다르다는 이유만으로 통합하지 마세요. [SSO 및 제품별 접근]

02.5Active sessions — 계정 세션 확인

2026년 6월 2일 릴리스 노트 기준, 사용자는 Settings → Security → Active sessions에서 본인 계정에 연결된 OpenAI 자체 세션을 확인하고 개별 또는 전체 로그아웃을 실행할 수 있습니다.

  • 표시 항목은 기기, 앱, 대략적 위치, 로그인 시각, 신뢰된 기기 여부, 현재 세션 여부 등입니다.
  • 범위에는 ChatGPT, Codex, API Platform 세션이 포함될 수 있지만, 타사 앱 세션이나 타사 서비스용 Sign in with ChatGPT 세션은 관리하지 않습니다.
  • 조직 SSO(SAML/OIDC)에 연결된 계정에는 제공되지 않을 수 있고, Codex CLI 세션도 여기서 관리하지 않습니다.

02.6Library — 파일 저장소와 자동 참조

Library에 업로드·생성한 파일을 저장해 검색하고 대화에 다시 첨부할 수 있습니다. Enterprise/Edu/Healthcare 파일은 워크스페이스 보존 정책을 따릅니다.

  • Owner는 자동 참조를 제어합니다. 꺼도 검색·열기·수동 첨부는 가능합니다. Healthcare에서는 자동 참조가 기본 OFF입니다.
  • 공유 지원 환경에서는 파일·폴더를 특정 사람 또는 워크스페이스에 공유하고 Viewer / Editor 권한을 지정합니다. 받은 콘텐츠는 Shared with me에서 찾습니다.
  • 관리자가 공유를 끄면 새 공유·권한 변경이 차단되지만 기존 공유 접근은 유지됩니다. 공유 폴더의 업로드 파일은 폴더 소유자에게 귀속됩니다.
  • Google Drive·Box·Dropbox·SharePoint 탐색에는 연결 계정의 파일 접근 권한이 필요합니다. 필요한 public actions를 모두 허용해야 하며, 재연결 또는 제공업체 관리자 승인이 필요할 수 있습니다.
  • Google Drive 초기 범위는 My Drive와 직접 공유된 항목이며 Shared Drives는 아직 포함되지 않습니다. 원본 접근 권한을 따르고, 지원·승인된 작업은 원본을 직접 수정할 수 있습니다.
  • Compliance 관리자는 Library 전용 endpoint로 내보내기·삭제할 수 있습니다.

02.7Improved memory — 개선된 메모리

Enterprise/Edu의 개선된 메모리는 역할별 접근 설정을 따릅니다. 메모리가 켜져 있으면 ChatGPT는 수동 저장 메모리만이 아니라 과거 대화의 관련 맥락을 참조해 더 최신의 개인화 응답을 제공할 수 있습니다.

  • 사용자는 메모리 요약을 검토하고, 개인화 응답 아래에서 어떤 메모리·과거 대화·custom instructions가 근거로 쓰였는지 볼 수 있습니다.
  • 관리자는 Permissions & roles에서 기본 역할 또는 Custom Role의 Use shared memory → Use improved memory를 확인합니다.
  • Healthcare 및 Regulated Workspace의 improved memory는 기본 OFF이며 BAA 적용 기능이 아닙니다. 해당 기능에 PHI를 입력하지 않도록 안내합니다.
  • 관리자와 사용자는 legacy Saved memories로 되돌릴 수 있습니다.
  • Codex memory에는 영향이 없습니다. 프로젝트 전용 메모리는 프로젝트 안에만 머물며, 프로젝트 밖 메모리나 대화를 사용하지 않습니다.

Workspace settings → Members

  • Seat 변경 — seat type이 제공되는 워크스페이스에서는 Owner가 Workspace settings → Members → ··· → Change seat type으로 변경할 수 있습니다. 옵션이 보이지 않으면 OpenAI account team에 요청합니다. 특히 ChatGPT seat → Codex seat 전환 전에는 chats, memories, projects, shared projects 같은 ChatGPT 데이터 가시성 변화 여부를 먼저 검토해야 합니다.
  • Pending invites/Requests — 보류 중 초대·가입 요청에서도 선택된 seat type을 함께 검토하며 승인/재전송/수정/거절합니다.
  • 멤버 제거 — ··· 메뉴 → Remove member.
  • 기본 seat 타입(Default seat type) 설정 — 이후 신규 가입자(SCIM 포함)는 이 값으로 발급.

Section 04 · ChatGPT

Groups — 그룹

Admin Console → Users & groups · Workspace settings → Groups

그룹은 RBAC(역할 기반 접근 제어)와 GPT/프로젝트 공유의 “단위”입니다. 대상 Enterprise/Edu에서는 관리자 콘솔(Admin Console)이 멤버·그룹·역할·권한·일반 설정과 테넌트 전역 SCIM의 중앙 관리 화면이며, 기존 Workspace settings 링크는 해당 관리자 콘솔 화면으로 연결될 수 있습니다.

  • 그룹 생성·삭제, 멤버 추가/제거
  • 그룹 멤버십 검토
  • SCIM 동기화 그룹은 이름 옆에 SCIM 배지가 표시되어 직접 관리 그룹과 구분
  • 테넌트 전역 SCIM은 지원되는 ChatGPT workspace와 Ads account에 product access를 배정하지만 API Platform organization은 프로비저닝하지 않습니다.
  • 워크스페이스 단위 SCIM도 계속 지원됩니다. 연결된 ChatGPT workspace 또는 API organization에 product-level SCIM이 활성 상태이면 tenant-wide SCIM을 켤 수 없으므로, 작동 중인 연결을 삭제하지 말고 승인된 마이그레이션을 먼저 계획합니다.
  • tenant-wide SCIM은 같은 이름의 수동 그룹을 인수하지 않고 별도 동기화 그룹을 만들 수 있습니다. workspace-level SCIM은 구성에 따라 기존 동명 그룹을 IdP 관리로 전환할 수 있으므로 범위를 구분해 확인합니다.
RBAC 할당 기준
그룹은 대규모 운영에 권장되지만, 최신 전용 RBAC 문서는 지원되는 환경에서 Custom Role을 그룹 또는 개인 사용자에게 직접 할당할 수 있다고 설명합니다. [RBAC] · [SCIM]

04.1Group managers — 그룹 관리자 위임

Enterprise의 Owner/Admin은 기존 그룹 멤버를 Group manager로 지정하고 별도로 위임 권한을 선택합니다. 이 지정은 workspace Admin/Owner 또는 테넌트 User manager 역할을 부여하지 않습니다.

  • 위임 가능: View group analytics / Manage spend controls / Manage model access and defaults.
  • Edit permissions on assigned roles의 위임은 Owner만 변경할 수 있습니다. 여러 그룹이 같은 Custom Role을 공유하면 역할 수정이 모든 대상 그룹에 영향을 줍니다.
  • 그룹 생성·삭제, 역할 할당/해제, 그룹 관리자 임명 및 자기 권한 확대는 위임에 포함되지 않습니다. SCIM 멤버십은 IdP에서 관리합니다.

→ 그룹 관리자 권한과 범위

04.2멤버·그룹·역할의 Admin API 자동화

2026-08-20 Invitations / Users API: 초대 조회·생성·재전송·삭제와 가입 완료 멤버 조회를 자동화합니다. 멤버의 기본 역할·seat 변경과 workspace 탈퇴 처리는 Owner 권한이 필요하며, SCIM 관리 변경은 IdP를 통하고 마지막 Owner 보호가 적용됩니다. 2026-09-11 Groups API는 대상 workspace에서 그룹 생성·수정·삭제를 지원합니다. Credentials → Admin keys에서 해당 workspace의 최소 필요 권한을 부여합니다. Group manager 지정만으로 Admin key 사용 권한을 얻지는 않습니다. [8/20·9/11 릴리즈 노트] · [Admin key 권한]

Workspace Roles and Permissions API: Custom Role과 그룹의 역할 할당을 관리합니다. 조회는 활성 Owner/Admin + chatgpt.enterprise.rbac.read, 변경은 활성 Owner + chatgpt.enterprise.rbac.write가 필요합니다. Admin은 write scope가 있어도 변경할 수 없습니다. 이 API의 Custom Role·그룹 할당과 Users API의 기본 멤버 역할·seat 변경을 구분하며, 개인 사용자에게 Custom Role을 직접 할당하는 변경 API는 포함하지 않습니다. [RBAC API 범위]

Section 05 · ChatGPT

Permissions & Roles — 핵심 거버넌스 탭

Workspace settings → Permissions & Roles

Enterprise/Edu 관리자에게 가장 중요한 한 화면. 워크스페이스 전체에 적용되는 기본 권한, 그리고 그룹 또는 지원되는 경우 개인 사용자에게 할당할 Custom Role을 만드는 곳입니다.

05.1Default permissions(기본 권한)

워크스페이스의 기본 권한입니다. Custom Role의 Default는 이 값을 상속하고, On은 해당 역할에서 허용, Off는 해당 역할에서 거부를 뜻합니다.

최신 유효 권한 계산
여러 일반 Custom Role은 가산적으로 결합됩니다. 한 역할이 On이면 다른 일반 역할의 Off가 그 허용을 무효화하지 않습니다. 더 강한 네트워크 제한이 필요하면 별도로 평가되는 Lockdown Mode를 사용합니다. [RBAC 가이드]

Owner는 Custom Role을 그룹에 할당하며, 기능이 제공되는 환경에서는 개인 사용자에게 직접 역할을 할당할 수도 있습니다. 그룹은 규모 있는 운영과 SCIM 기반 수명주기 관리에 계속 권장됩니다.

05.2Custom Roles — 토글 가능한 권한 카테고리

각 Custom Role 안에서 다음 항목을 개별 ON/OFF 할 수 있습니다(최신 공식 RBAC 기준).

  • Canvas — 캔버스 코드 실행 / 네트워크 접근 기본값
  • ChatGPT agent — 에이전트 모드(웹 자동 조작) 사용
  • Codex — Codex 사용 및 인터넷 접근 관련 제어(아래 Codex 섹션 참조)
  • Apps — 앱 사용 허용 여부, 앱별 선택, action 단위 제어
  • Deep research — Work/Codex에서도 Deep research 권한과 Web search 활성화가 필요합니다.
  • Data 플러그인 — Plugins의 설치 정책과 역할·그룹 접근을 제어하며, 데이터 소스 앱은 별도 연결·권한이 필요할 수 있습니다.
  • Library 공유 — 새 공유와 공유 권한 변경을 제어합니다. OFF로 바꿔도 기존 공유 접근은 유지됩니다.
  • GPTs — 생성·편집·공유 범위(invite-only / workspace / public), 서드파티 GPT 접근
  • Projects — 프로젝트 생성·편집 권한
  • Record — 과거 노트·녹취/기록 참조 권한
  • Search — 웹 검색, 에이전트 검색
  • Shared projects — 공유 프로젝트 참여
  • Skills — Skill 생성·사용, skill 파일 업로드, 공유, 워크스페이스 게시, 다른 멤버용 설치
  • Link sharing — 대화 링크 공유 범위
  • Available models — 이 Role이 쓸 수 있는 모델 한정
  • Usage limits / Spend controls — 크레딧/메시지 한도(아래 참고)

여러 일반 Custom Role을 동시에 가진 사용자는 합집합(가산적 허용)으로 해석됩니다. Seat type, plan, product eligibility는 별도로 적용됩니다.

참고로 Apps는 앱 단위 접근은 제어할 수 있지만, 앱 UI 자체를 개별로 숨기는 방식은 아닙니다.

Lockdown Mode 역할
Lockdown Mode를 지원하는 워크스페이스에서는 이를 단일 토글이 아니라 역할 수준 보안 구성으로 다룹니다. 해당 역할을 받은 멤버는 live web search, deep research, agent mode, Canvas 네트워크, 일부 앱/MCP/connector 동작이 제한될 수 있으므로, 할당 전 각 앱과 action, 원본 시스템 권한을 함께 확인해야 합니다.

05.3Spend controls (Usage limits / overages)

크레딧 기반 Enterprise 계약에서는 shared credit pool에서 대상 기능의 사용량이 차감됩니다. 비용과 한도를 자동화할 때는 선택한 workspace의 청구 방식과 API 응답 단위를 먼저 확인합니다. 공식 Usage limits 문서는 이제 사용자별 월간 한도와 워크스페이스 overage limit을 별도 제어로 설명합니다. Usage limits는 Admin Console에서, overage limit과 usage alert는 선택한 workspace의 Billing에서 관리합니다. [Flexible pricing]

  • Usage limits: Admin Console → ChatGPT workspace 선택 → Usage limits에서 workspace 기본값, group 기본값, user override를 설정합니다.
  • 사용 기간: 기본 Monthly는 매월 1일 UTC에 초기화되고, 제공되는 경우 Aligned to billing cycle은 workspace 청구 주기 시작일에 맞춰 초기화됩니다.
  • 적용 순서: user override → 사용자가 속한 그룹 중 가장 높은 group limit → workspace default 순으로 적용됩니다.
  • 증액 요청: Usage limits → Pending Requests 승인 또는 Users 탭에서 임시 / 영구 사용자 재정의를 선택합니다. 임시는 현재 사용 기간 말에 만료되어 그룹/워크스페이스 기본값으로 돌아가며, 영구는 변경·삭제 전까지 유지됩니다. 임시 옵션은 사용자 재정의에만 적용됩니다.
  • 그룹 관리자: Enterprise에서 Manage spend controls를 위임받으면 담당 그룹의 한도와 증액 요청을 관리할 수 있습니다. 워크스페이스 기본값·사용 기간·청구·overage 설정 변경 권한은 포함되지 않습니다.
  • 기존 주간 제한과의 관계: legacy weekly role-based limit이 남아 있으면 Admin Console의 migration banner에서 Usage limits → Workspace → Migrate now를 실행합니다. 배너가 없으면 이미 이전되었거나 대상이 아닐 수 있습니다.
  • Overage limit: shared credit pool이 먼저 소진되면 Global Admin Console → Billing의 workspace overage limit이 추가 사용 가능 범위를 결정합니다. user usage limit은 overage 사용 중에도 계속 적용됩니다.
  • No limit 의미 차이: Usage limits의 group override에서 No limit은 workspace default 상속을 뜻하지만, Billing의 workspace overage limit에서 No limit은 overage cap이 설정되지 않았다는 뜻입니다.
  • Usage alerts: 크레딧 기반 workspace에서는 credit threshold, committed credits 소진, overage limit 도달 시 알림을 보낼 수 있지만 사용을 차단하지는 않습니다. 차단이 필요하면 overage limit을 설정합니다.
  • 운영 패턴: 엔지니어링/AI 챔피언 그룹은 넉넉한 group default, 일반 사용자 그룹은 보수적 default, 예외 사용자는 user override로 관리하는 편이 명확합니다.
  • 관찰 위치: Usage limits는 제한·차단선, Billing/credit analytics는 비용 운영, Workspace analytics는 채택·활동 분석입니다. 같은 화면을 복제하는 구조가 아니므로 숫자가 일시적으로 다를 수 있습니다.
Spend Controls API — 금액과 단위를 함께 지정

지원되는 workspace에서는 Admin API로 workspace·group·user 한도를 조회하고 수정할 수 있습니다. 2026-09-10 API v2.5.18 기준으로 새 연동은 limit_amount를 사용합니다.

  • 청구 단위: USD workspace의 예시는 "limit_amount": {"amount":"250.00","unit":"usd"}입니다. 크레딧 workspace는 unit: "credit"을 사용합니다. workspace와 같은 단위를 지정해야 하며, API는 달러와 크레딧을 자동 환산하지 않습니다.
  • 기존 연동 이전: 정수형 limit은 크레딧 전용 legacy 필드이며 deprecated 상태입니다. USD workspace에서 기존 숫자를 그대로 재사용하지 말고 금액과 단위를 명시하세요.
  • 현재 사용량: current_month_usage_unit을 함께 읽어 사용량 단위를 확인합니다. 응답의 숫자를 일괄 크레딧으로 해석하지 않습니다.
  • 권한: 조회에는 chatgpt.enterprise.usage_limit.read, 변경에는 chatgpt.enterprise.usage_limit.write 권한이 있는 해당 workspace의 Admin key를 사용합니다.
  • 사용 기간: API로 Monthly / Aligned to billing cycle을 변경할 수 없습니다. 사용 기간은 Admin Console에서 설정합니다.

05.5Workspace Agents 점진 배포

최신 공식 가이드 기준, Workspace Agents는 대상 Enterprise/Business 워크스페이스뿐 아니라 EKM이 적용된 대상 Enterprise 워크스페이스까지 지원합니다. 에이전트는 ChatGPT와 Slack에서 반복 업무를 자동화할 수 있으며, 앱·파일·스킬·커스텀 MCP 서버를 연결하고 예약 실행도 가능합니다.

  • 기본값: 출시 시점에는 OFF
  • 관리 포인트: agent 생성, 게시, Slack 사용 권한 제어
  • 게시 권한 세분화: 관리자는 워크스페이스 디렉터리에 publish할 수 있는 역할을 Role 단위로 제어할 수 있음
  • 공유 방식: 비공개, 링크 공유, 워크스페이스 디렉터리
  • 주요 기능: 템플릿/직접 생성, guided setup, 미리보기, 예약 실행, 버전 히스토리, usage analytics
  • 응답 기능: 사용 가능한 모델·reasoning effort 선택, audio 파일 생성, Slack thread 후속 응답 여부 제어
  • EKM 상태: 출시 초기 제한은 해제되었고, 이제 대상 EKM Enterprise도 사용 가능
  • Codex plugin 경계: Codex의 Workspace Agents plugin도 같은 Workspace Agents RBAC를 따르며, 사용자의 Workspace Agents 권한을 끄면 plugin에서도 사용할 수 없습니다. 별도의 Codex-only 토글로 분리되지 않습니다.
  • API trigger: 외부 시스템에서 실행하려면 Agent builder에서 API channel을 추가하고 agent를 publish해야 합니다. 실행에는 Workspace Agent access token을 사용하며, Codex access token과 구분합니다.
  • Draft/publish: Codex plugin은 draft agent를 만들고 수정할 수 있지만, schedules/API channel을 포함한 변경은 publish 전까지 활성 agent에 반영되지 않습니다.
  • 공유 인증: Slack이나 외부 앱을 연결하는 agent는 개인 계정보다 agent 전용 shared connection 또는 service account와 최소 권한 원칙을 우선 검토합니다.
  • 가격 메모: Enterprise Workspace Agent 실행은 현재 token 기반 credit 과금이 적용됩니다. 고정 task 비용이 아니라 input, cached input, output token 구성에 따라 credit이 달라집니다.

05.6ChatGPT Work · Scheduled tasks 점진 배포

2026년 7월 16일 업데이트 기준, ChatGPT desktop app은 상단 전환기에서 ChatGPT / Codex를 구분하고, ChatGPT 안에서 Chat / Work를 전환합니다. Chat은 질문·짧은 작성, Work는 조사·분석·문서·스프레드시트·프레젠테이션·Site 같은 완성 산출물, Codex는 코드 작성·테스트·리뷰·리포지토리 작업에 초점을 둡니다.

  • 기본 활성화: 대상 Enterprise/Edu의 default workspace role에서는 Work가 기본 활성화될 수 있으며, Owner/Admin이 Workspace settings와 RBAC로 끌 수 있습니다. 계정별 rollout 상태는 다를 수 있습니다.
  • 데스크톱 기록: Chat과 Work는 Recents와 Projects를 공유합니다. Cloud Work conversation은 web/mobile/desktop 간 동기화되고, local conversation은 해당 컴퓨터에 남습니다.
  • Codex 분리: Codex는 별도 view와 별도 history를 유지하며 web/mobile의 Chat/Work 전환 대상이 아닙니다. 다만 mobile의 Remote tab에서 지원되는 desktop Codex chat을 이어볼 수 있습니다.
  • 관리 경계: Work가 사용하는 Plugins, Apps, Skills와 연결 원본 권한은 기존 workspace RBAC, 앱 action control, source-system 권한을 그대로 따릅니다.
  • Scheduled tasks: 한 번 실행, 반복 일정, 이벤트 트리거, 변경 모니터링으로 Work/Codex 작업을 백그라운드에서 실행할 수 있습니다.
  • 이벤트 트리거: Gmail 새 메일, Slack 채널 메시지, GitHub pull request 활동을 지원합니다. Enterprise/Edu에서는 Permissions & roles → Work → Allow event-triggered scheduled tasks가 기본 OFF이며, Work·승인된 앱·필요 action 권한도 함께 필요합니다.
  • 공유: Share chats and scheduled tasks in the workspace가 별도 권한입니다. 수신자는 같은 workspace 멤버여야 하며, 공유 링크에서 자신의 별도 copy를 예약하고 자신의 연결 앱 권한을 사용합니다.
  • Surface 제한: 이벤트 트리거 생성·편집은 web과 지원 mobile에서 하고, desktop app·Codex CLI·IDE에서는 새 이벤트 조건을 만들 수 없습니다.
  • 로컬 실행: 데스크톱 앱의 scheduled task가 로컬 프로젝트를 쓰면 컴퓨터와 앱이 켜져 있어야 하며, local project 또는 격리 worktree를 선택할 수 있습니다.
  • 보안 기준: unattended run은 기본 sandbox 설정을 사용하므로, 필요한 최소 filesystem/network 권한만 허용하고 첫 실행 결과를 검토해야 합니다.
  • 비용 기준: Work는 Codex와 같은 usage structure를 따르며, 긴 작업·여러 source·tool 사용은 더 많은 credit을 사용할 수 있습니다.
  • Deep Research: Work/Codex에서 @Deep Research로 시작하며 기존 Work/Codex 사용량 또는 크레딧을 사용합니다. Chat의 별도 deep research 작업 한도는 차감하지 않습니다.
  • ChatGPT Voice: Voice가 허용되면 Live가 기본이며 Early Model Access는 필요하지 않습니다. 검색·추론에 사용할 GPT-5.6 또는 GPT-6 Astra와 추론 수준은 텍스트 채팅과 같은 모델 제어에서 선택합니다. 모델 권한이 적용되며, 검색·추론 사용량은 음성 시간과 별도로 계산합니다.

현재 App permissions: Always ask(읽기·변경 전 확인), Allow read actions(읽기는 자동, 변경 전 확인), Allow low-risk actions(저위험 자동, 고위험 확인 또는 거부), Allow all actions(지원되는 개별 앱에만 제공 가능). 마지막 옵션은 표준 워크스페이스 전체 선택기에 없습니다. 권한 설정은 provider 승인·동작 제한·안전 보호를 우회하지 않습니다. [앱 권한]

Codex access tokens for automation

브라우저 로그인 없이 신뢰된 자동화가 ChatGPT 워크스페이스 ID로 Codex Local을 실행해야 할 때 쓰는 토큰입니다. 일반 OpenAI API 호출이면 Platform API key를 계속 쓰고, Codex 실행이 워크스페이스 권한·감사·사용량에 연결되어야 할 때만 access token을 사용합니다.

  • 관리 토글: Codex Local을 켠 뒤 Allow members to use Codex access tokens를 켭니다.
  • 만료 한도 제어: Owner/Admin은 Workspace Settings → Permissions & roles → Codex Local에서 Access token expiration limit를 정해, 멤버가 선택할 수 있는 최대 만료 기간을 제한할 수 있습니다. 이 제한은 신규 토큰에만 적용됩니다.
  • 좁은 배포: Custom Role을 쓰는 조직은 access token 권한을 필요한 그룹에만 부여합니다.
  • 일회성/비영구 자동화: CODEX_ACCESS_TOKEN 환경변수에 저장하고 codex exec를 실행합니다.
  • 영구 로컬 로그인: printf '%s' "$CODEX_ACCESS_TOKEN" | codex login --with-access-token을 사용합니다.
  • 운영 원칙: secret manager에 저장하고, 로그·티켓·채팅에 노출하지 않으며, 가능하면 7/30/60/90일 같은 유한 만료일을 두고 정기 회전·폐기합니다.

12.6Computer Use / Browser Developer mode

ChatGPT desktop app의 Work/Codex는 지원 지역의 macOS와 Windows에서 Computer Use를 제공합니다. EEA·영국·스위스도 2026년 6월부터 순차 배포가 시작됐으므로 실제 가용성은 해당 계정·워크스페이스에서 확인합니다. Windows에서는 Computer Use가 active desktop foreground에서 동작하므로, 사용자가 같은 Windows 세션을 동시에 쓰는 동안 백그라운드 자동화처럼 운영할 수 없습니다.

  • 설치: Codex settings → Computer Use에서 plugin을 설치합니다. macOS는 Screen Recording과 Accessibility 권한이 필요합니다.
  • Record & Replay: macOS에서는 반복 업무를 한번 시연해 재사용 가능한 skill로 만드는 Record & Replay가 추가되었습니다. Computer Use가 켜져 있어야 하고, 조직이 [features].computer_use = false로 막아 두면 함께 비활성화됩니다.
  • Computer History: Enterprise macOS에서 관리자 role permission과 사용자별 opt-in이 모두 필요하며 기본 OFF입니다. screenshot·screen recording·microphone·system audio가 아니라 선택한 앱/웹사이트의 interaction event를 기록합니다. Memories가 필요하고 사용자는 pause·대상 앱 선택·timeline 삭제가 가능합니다.
  • Apple Messages: Apple silicon Mac에서는 Work/Codex가 Messages의 iMessage/SMS/RCS를 검색하고 메시지를 준비하거나 보낼 수 있습니다. 기본적으로 발송 전 사용자 승인을 요청하며, 관리자는 기존 Computer Use 제어로 비활성화할 수 있습니다.
  • Windows 운영: target app을 화면에 보이게 두고, 장시간 작업은 기기를 잠금 해제·인터넷 연결 상태로 유지하거나 VM/원격 제어 조합을 권장합니다.
  • 사이트·앱별 정책: 브라우저 오리진별 기록·업로드·다운로드·전체 CDP 접근·승인 유지와 macOS/Windows 앱별 접근을 중앙 제어합니다. Windows는 검증된 AUMID 또는 실행 파일 서명 정보로 식별합니다. 세부 키와 적용 경계는 Section 14.5를 참조합니다.
  • 관리자 제어: requirements.toml에서 [features].computer_use = false로 Computer Use, Record & Replay, 관련 설치·활성화 흐름을 비활성화할 수 있습니다.
  • Browser Developer mode: Browser use에서 CDP 기반 성능 프로파일링, console/network/DOM/style 진단을 허용합니다. 사용자 기본값은 OFF이며, 관리자는 [features].browser_use_full_cdp_access = false로 비활성화할 수 있습니다.
  • Browser/Computer Use 전체 차단: Browser Use, 외부 브라우저, in-app browser, Computer Use를 모두 막아야 하면 [features].browser_use = false, browser_use_full_cdp_access = false, browser_use_external = false, in_app_browser = false, computer_use = false를 함께 고정합니다.
  • Appshots: 9월 11일 기준 Windows의 전경 앱도 캡처할 수 있습니다. macOS는 양쪽 Command, Windows는 양쪽 Alt 또는 사용자 지정 단축키를 사용합니다. 전경 창의 이미지와 제공되는 텍스트가 첨부되며, 관리자는 allow_appshots = false로 차단할 수 있습니다.
  • 기타 UX: app composer의 /init은 AGENTS.md scaffold를 생성하고, usage-limit 오류는 가능한 경우 워크스페이스 안내와 reset timing을 더 명확히 보여주며, command menu에는 Unread chats 섹션이 추가되었습니다.

개발자 노트북에 디바이스 파일을 직접 뿌리지 않고도, 그룹별로 다른 Codex 로컬 제약을 적용할 수 있는 화면입니다. 지원되는 App / CLI / IDE가 시작할 때 로그인 ID에 맞는 서명된 캐시 또는 서버 정책을 불러옵니다. 백그라운드 정책 갱신은 다음 실행에 반영되므로, 실행 중인 세션까지 즉시 바뀐다고 안내하지 않습니다.

14.1제어 가능한 항목

  • allowed_approval_policies — 허용할 승인 동작을 제한. approval_policy = "untrusted" 직접 설정은 지원 종료되었고, on-failure는 deprecated입니다. 대화형 실행은 on-request를 기준으로 검토하며 프로젝트 신뢰 설정은 Section 15.7에서 별도로 다룹니다.
  • allowed_approvals_reviewers / guardian_policy_config — 자동 검토자 허용 여부와 테넌트별 자동 검토 정책 조정
  • allowed_sandbox_modes — 레거시 배포용 sandbox mode 허용 목록. Codex 0.138.0+에서는 가능하면 permission profile 기반 정책으로 옮기는 편이 맞습니다.
  • allowed_permission_profiles / default_permissions — 0.138.0+ 기준 권장 방식. :read-only, :workspace 같은 built-in 또는 조직 정의 custom profile의 허용 목록과 기본값을 중앙 제어합니다.
  • [[remote_sandbox_config]] — 호스트 패턴별 샌드박스 요구사항 오버라이드
  • allowed_web_search_modes — disabled / cached / live
  • [permissions.filesystem].deny_read — 정확한 경로 또는 glob 패턴 기준 읽기 차단
  • MCP 서버 허용 목록 — 어떤 MCP 서버만 허용할지 이름과 identity가 모두 일치해야 허용. 빈 배열이면 전 MCP 차단
  • Managed hooks — [hooks]와 관리형 스크립트 디렉터리로 lifecycle hook 강제
  • Restrictive command rules — rm, git push 같은 위험 명령에 prompt/forbidden 적용
  • allow_remote_control = false — mobile/다른 기기에서 host를 제어하는 Remote Control access를 관리형으로 차단
  • allow_appshots = false — Appshots를 관리형으로 차단
  • [features].in_app_updates = false — 지원되는 macOS/Windows build에서 ChatGPT desktop app의 앱 내 업데이트를 차단. 이 경우 조직이 보안 수정 포함 새 build를 신속히 MDM으로 배포해야 하며 OpenAI는 version pinning, 별도 stable channel, 구버전 extended support를 제공하지 않습니다.
  • Browser Use, external browser, in-app browser, Computer Use 등 특정 사용 환경 비활성화
  • Browser/Computer Use 계열을 넓게 차단하려면 [features].browser_use = false, browser_use_full_cdp_access = false, browser_use_external = false, in_app_browser = false, computer_use = false를 함께 고정
  • approval_policy.granular 계열 — 지원되는 클라이언트에서 sandbox/rules/MCP elicitation/request permission/skill approval 같은 승인 범주를 더 세분화
  • 대상 Enterprise 워크스페이스에서 기본 제공되는 plugin sharing을 조직 정책상 꺼야 할 때 MDM 또는 cloud-managed requirements로 비활성화

14.2예시 정책

default_permissions      = ":workspace"
allowed_approval_policies = ["on-request"]
allowed_web_search_modes  = ["disabled", "cached"]

[allowed_permission_profiles]
":read-only" = true
":workspace" = true
# ":danger-full-access" is omitted, so it stays denied.

[rules]
prefix_rules = [
  { pattern = [{ token = "rm" }], decision = "forbidden",
    justification = "Use git clean -fd instead." },
  { pattern = [{ token = "git" }, { any_of = ["push", "commit"] }],
    decision = "prompt",
    justification = "Require review before mutating remote history." },
]

14.3그룹 할당 & 폴백

  • 각 정책을 특정 사용자 그룹에 할당
  • 매칭되지 않는 사용자용 기본(default fallback) 정책 별도 지정
  • 그룹 간 정책 선택은 현재 관리 서비스가 결정합니다. 여러 그룹에 속한 실제 사용자로 적용 결과를 확인하고, 첫 매칭 같은 알고리즘을 고정 가정하지 않습니다.

14.5브라우저 오리진 · 네이티브 앱 정책

2026년 9월 기준 지원 클라이언트에서는 [browser_use]와 [computer_use]로 사이트·앱별 접근을 제한합니다. 오리진(origin)은 https://example.com:8443처럼 프로토콜·호스트·포트로 구성하며 경로는 넣지 않습니다.

대상관리형 제어
브라우저 기록browser_use.allow_history_access = false로 Browser Use의 기록 읽기를 차단합니다. Computer History 기능과 별개입니다.
사이트별 동작default_origin_policy와 origins에서 access, uploads, downloads, full_cdp_access를 allow/deny로 설정합니다. 전체 CDP(Chrome DevTools Protocol) 접근은 브라우저 디버깅 권한입니다.
자동 검토browser_use.disable_auto_review = true 또는 오리진의 auto_review = "deny"로 사용자 승인으로 전환합니다. 모델 안전 모니터링은 계속 적용됩니다.
저장된 승인allow_global_persistent_approval = false는 모든 사이트에 대한 Always allow를 무시하며 삭제하지 않습니다. 오리진의 persistent_approval = false는 해당 사이트의 영구 승인을 제한합니다. access_approval_lifetime은 turn 또는 thread이며 기본은 thread입니다.
브라우저 데이터 가져오기in_app_browser.allow_external_browser_settings_import = false로 외부 브라우저 설정·방문 데이터 가져오기를 차단합니다. 관리형 전용 키입니다.
네이티브 앱computer_use.default_app_access로 기본 접근을 정하고, macOS는 computer_use.macos.bundle_ids, Windows는 computer_use.windows.aumids 또는 computer_use.windows.exes로 앱을 식별합니다. EXE 규칙은 검증된 publisher_name, product_name, access가 필수이고 binary_name은 선택입니다.
앱 승인 유지computer_use.allow_persistent_approval = false로 세션 간 저장 승인을 막습니다. 현재 세션 승인은 가능합니다.

여러 오리진 규칙이 겹치면 항목별로 더 제한적인 값이 적용됩니다. 로컬 설정은 관리형 deny를 완화할 수 없으며, allow는 OS 권한·플러그인 설치·사용자 승인을 대신하지 않습니다. 명령 네트워크 allowlist와 사이트 오리진 정책을 각각 검증합니다.

Managed Configuration — OS별 완전 가이드

Cloud-managed requirements 외에도 각 사용자 PC에 정책 파일을 직접 배포해 Codex 동작을 강제할 수 있습니다. 이 섹션의 핵심은 OS마다 적용 방식·경로·한계가 모두 다르다는 점이며, 잘못 설계하면 정책이 강제되지 않거나 사용자가 우회할 수 있습니다.

→ Codex Managed Configuration 공식 가이드

15.1Requirements 적용 우선순위

현재 공식 문서의 우선순위는 아래로 갈수록 높습니다. 사용자 기본 설정은 강제 requirements를 넘을 수 없습니다.

  1. 시스템 requirements.toml — Unix의 /etc/codex/requirements.toml, Windows의 %ProgramData%\OpenAI\Codex\requirements.toml
  2. Cloud-managed requirements — 로그인된 워크스페이스의 클라우드 정책
  3. 레거시 managed_config.toml 중 클라이언트가 requirements로 재해석하는 필드
  4. macOS MDM — com.openai.codex:requirements_toml_base64

일반 scalar/list는 상위 소스가 덮어쓰고, table은 키별 병합됩니다. rules·hooks·파일 접근 제약은 필드별 결합 규칙을 따르므로 모든 항목이 동일하게 병합된다고 가정하지 않습니다.

0.138.0+ 권장 기준
최신 공식 문서는 Codex 0.138.0 이상에서 allowed_sandbox_modes보다 permission profile 방식(allowed_permission_profiles + default_permissions)을 우선 권장합니다. 구버전 클라이언트(0.137.x 이하)는 이 키들을 무시할 수 있으므로, fleet 업그레이드 상태를 먼저 확인해야 합니다.
중요한 경계
Managed configuration은 Codex local runtime의 동작을 제약하지만, ChatGPT 워크스페이스 접근, seat 부여, 역할/RBAC를 대신 부여하지 않습니다. 사용 권한은 Workspace settings와 Global Admin Console에서 먼저 설계하고, managed configuration은 클라이언트 실행 정책으로 운영합니다.

15.4공통 정책 예시

아래 TOML은 OS와 무관하게 동일하게 작성합니다. 차이는 “어디에 두느냐”뿐입니다.

# 보수적인 기본값 (0.138.0+ 권장)
allowed_approval_policies = ["on-request"]
default_permissions = ":workspace"

[allowed_permission_profiles]
":read-only" = true
":workspace" = true

[experimental_network]
enabled = true
managed_allowed_domains_only = true

[otel]
environment      = "prod"
exporter         = "otlp-http"
log_user_prompt  = false  # 프롬프트 본문 저장 금지(기본)
macOSMDM 기반 배포 가장 강력한 OS 레벨 강제

파일 위치

  • 관리형 기본값: /etc/codex/managed_config.toml
  • 요구사항(잠금): /etc/codex/requirements.toml
  • MDM 프로파일 도메인: com.openai.codex
  • MDM 키: config_toml_base64 (기본값) / requirements_toml_base64 (잠금)

MDM 워크플로 (Jamf Pro / Kandji / Fleet / Mosyle 공통)

  1. 위 TOML을 작성
  2. base64로 인코딩 (줄바꿈 없는 단일 라인으로): 
    cat requirements.toml | base64 | tr -d '\n' > requirements.b64
  3. MDM 프로파일에 다음 페이로드 추가: 
    <dict>
  <key>PayloadType</key>
  <string>com.openai.codex</string>
  <key>requirements_toml_base64</key>
  <string>[base64 인코딩 문자열]</string>
</dict>
  4. 대상 디바이스에 푸시 → 사용자에게 Codex 재시작 요청
  5. Codex 시작 로그(config summary)에 (managed) 표시 확인
  6. 정책 변경 시 페이로드만 갱신하면 다음 실행 때 자동 재적용

15.7지원 종료 승인 정책 · 로컬 인증 제약

  • approval_policy = "untrusted"를 사용자·프로젝트·프로파일·시작 옵션·관리형 기본값에서 제거합니다. on-failure도 deprecated입니다. 대화형 읽기 전용 작업은 on-request와 허용된 읽기 전용 profile을 검토합니다. 샌드박스가 허용하는 명령은 매번 승인받지 않습니다.
  • 더 엄격한 프로젝트 명령 승인이 필요하면 명시적 approval_policy를 생략하고, 사용자 ~/.codex/config.toml의 프로젝트 항목에 trust_level = "untrusted"를 설정하며 allowed_approval_policies에는 untrusted를 유지합니다. 이 방식은 프로젝트 로컬 설정도 비활성화합니다. 명시적 on-request는 이 파생 승인 동작보다 우선합니다.
  • allowed_login_methods, allowed_chatgpt_workspaces, cli_auth_credentials_store, chatgpt_base_url은 로컬 시스템 requirements 또는 macOS MDM으로 배포합니다. 클라우드 requirements에서는 무시되므로 인증 경계는 기기에서 먼저 적용해야 합니다.

  --data-urlencode "after=2026-09-01T00:00:00Z"
  • 목록 응답은 비용 합계가 아닌 파일 정보입니다. 파일을 다운로드해 처리하고, last_end_time으로 다음 목록을 조회합니다. 수집 시 event_id로 중복을 제거하고 지연 도착 데이터를 반영합니다.
  • 데이터는 UTC 시간별 보고 행이며 예상 지연은 3–5시간입니다. 사용자·그룹은 payload.identity, 제품·사용 환경·모델은 payload에서 확인합니다.
  • payload.measures.billing[].cost.unit은 CREDITS 또는 USD입니다. 같은 배열에 두 단위가 있을 수 있으므로 단위별로 합산합니다. USD 금액에 크레딧 환산율을 다시 곱하지 않습니다.
  • estimated_cost_usd는 크레딧 항목에만 제공되는 선택적 달러 추정치입니다. 실제 USD 항목까지 포함한 총액이 아닙니다. 기록된 비용과 이 추정치는 최종 청구서 금액과 구분합니다.

한도 제어 — Spend Controls

Spend Controls는 월 한도와 현재 사용량을 조회하고 workspace·group·user 한도, 사용자 일괄 변경, 증액 요청 승인·거절을 처리합니다. 상세 비용 배부에는 Costs를 사용합니다. 현재 기간에만 적용할 사용자 한도는 temporary: true, 만료 시점은 limit_expires_at으로 확인합니다. usage period 자체는 Console에서 설정하며 API로 변경하지 않습니다.

# 사용자 현재 월 사용량과 유효 한도 조회
curl "https://api.chatgpt.com/v1/manage/workspaces/$WORKSPACE_ID/usage_limits/users/$USER_ID/monthly-usage" \
  -H "Authorization: Bearer $CHATGPT_ADMIN_API_KEY"

현재 응답의 current_month_usage_unit과 한도의 limit_amount.unit을 함께 읽습니다. USD / credit 단위가 workspace 청구 방식과 일치해야 하며 자동 환산되지 않습니다. 신규 연동은 limit_amount를 사용합니다. 자세한 입력 형식과 이전 limit 필드 호환성은 Section 05.3을 확인합니다.

사용 분석 — 집계 기록과 제공 단계

  • Workspace Analytics 로그는 사용자·Project·GPT별 일일 활동과 설문 응답을 제공합니다. 현재 멤버·프로젝트 목록이 아닌 과거 보고 기록입니다. CHATGPT_USER_ANALYTICS.credits_used는 deprecated이며 새 기록에서 생략될 수 있으므로 비용 리포트의 필수 입력으로 두지 않습니다.
  • ChatGPT·Codex 통합 Daily Usage는 Alpha입니다. UTC 일일 사용자별 결과 또는 group=workspace 합계를 제공합니다. 제공 여부·지표 의미·필드는 정식 출시 전 변경될 수 있습니다.
  • Codex Turn Insights의 credits는 크레딧 과금, cost_usd는 직접 USD 과금입니다. 각각 집계하고, 확인 불가능한 USD의 null을 0으로 바꾸지 않습니다. 날짜는 양끝 포함 UTC 기준이며 최대 120일 범위입니다.

API Platform — 별도 사용량·비용

API Platform의 /organization/costs는 api_key_ids 필터와 project_id·line_item·api_key_id별 그룹 집계를 지원합니다. 모델·토큰·요청 수 분석은 해당 Usage endpoint의 지원 필드를 확인합니다. 모든 Usage API와 Costs API가 동일한 집계 차원을 지원한다고 가정하지 않습니다.

20.4④ Compliance API audit

Compliance API는 워크스페이스의 감사·컴플라이언스 데이터를 SIEM, 데이터 레이크, eDiscovery, DLP 도구로 가져오는 채널입니다. OpenAI Help 문서 기준 Compliance Logs Platform의 보존 기간은 30일이므로, 더 긴 보존이 필요하면 모든 로그를 지속적으로 다운로드해 고객 보존 정책에 맞춰 저장해야 합니다.

2026년 6월 5일 이후 기준 Compliance Platform 문서는 2026년 3월 5일 새 conversation logs 시스템이 릴리스되었고, 기존 stateful route는 2026년 6월 5일 제거되었다고 안내합니다. 현재 날짜 기준으로는 해당 제거일이 지났으므로, 기존 연동이 stateful route에 의존하지 않고 새 logs system 기준으로 마이그레이션되었는지 확인해야 합니다.

→ OpenAI Compliance Platform 공식 가이드

Policies & Configurations에서 변경한 Codex 제어 설정은 workspace 감사 로그에 기록됩니다. 지원되는 관리자 역할로 Admin Console에서 확인하거나, 필요한 로그 권한의 Admin key로 Compliance API에서 가져옵니다. 이벤트 구조와 실제 보존 범위는 현재 API reference를 확인합니다.

20.5Compliance API와 Platform Audit Log API 구분

운영 구분 Compliance API는 ChatGPT 워크스페이스의 사용자 활동, Codex, 인증, 감사 로그를 다루고, Admin/Audit Log API는 API Platform 조직의 API 키 생성, 프로젝트 관리, 멤버 변경 같은 관리 이벤트를 다룹니다. ChatGPT Enterprise와 API Platform을 함께 운영하는 조직은 두 로그 체계를 각각의 목적에 맞게 관리합니다.
