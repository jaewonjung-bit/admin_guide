Part 01

ChatGPT Enterprise · Workspace Settings 진입 경로

ChatGPT Enterprise(및 Edu)에서 관리자가 워크스페이스 전체 설정을 다루는 곳은 화면 좌측 하단 프로필 아이콘 → Workspace settings 메뉴입니다. 이 한 화면에 멤버, seat(사용권), 권한, GPT 거버넌스, 앱(연결), 분석, ID 공급자(SSO/SCIM) 등 거의 모든 항목이 모여 있습니다.

진입 경로
ChatGPT 좌측 하단 프로필 아이콘 → Workspace settings

Owner와 Admin은 모든 항목을 변경할 수 있고, 일반 Member는 이 화면 자체를 열 수는 있어도 핵심 설정(권한·seat·지출·기능 토글)을 바꿀 수 없습니다. [OpenAI 공식]

Section 02 · ChatGPT

General — 일반 설정

Workspace settings → General

워크스페이스의 “겉모습”과 “기본 정책”을 정하는 탭입니다. 이름과 로고처럼 사용자가 매일 보는 요소, 그리고 조직 전체에 일괄 적용되는 AI 사용 정책 모달이 여기에서 관리됩니다.

02.1Workspace name & image

이름 옆 연필(편집) 아이콘을 눌러 워크스페이스 이름·이미지를 바꿉니다. 저장하면 모든 멤버 화면에 즉시 반영됩니다.

02.2Workspace instructions

조직 차원에서 ChatGPT가 “어떻게 답해야 하는지” 알려주는 안내문입니다. 전사 톤앤매너, 금지 표현, 공통 용어 등을 적어두면 모든 대화의 시스템 프롬프트에 추가됩니다.

02.3Workspace policy modal

조직 고유의 AI 사용 정책을 적어두면, 사용자가 처음 로그인할 때(그리고 정책을 갱신할 때마다) 강제 모달로 표시되어 동의를 받습니다. 컴플라이언스/감사 대비용으로 유용합니다.

02.4Workspace & organization identifiers

워크스페이스 ID와 OpenAI 조직 ID(org-id)를 확인할 수 있습니다. Compliance API, Microsoft Purview, Tenable 등 외부 거버넌스 도구를 붙일 때 이 값을 사용합니다.

참고
ChatGPT Workspace의 org-id와 API Platform 조직의 org-id는 원칙적으로 동일합니다. 둘이 다르게 보인다면 별도 조직이 만들어져 있을 가능성이 높으므로 Account Director에게 통합을 요청하세요. [SSO 개요]

02.5Active sessions — 계정 세션 확인

2026년 6월 2일 릴리스 노트 기준, 사용자는 Settings → Security → Active sessions에서 본인 계정에 연결된 OpenAI 자체 세션을 확인하고 개별 또는 전체 로그아웃을 실행할 수 있습니다.

  • 표시 항목은 기기, 앱, 대략적 위치, 로그인 시각, 신뢰된 기기 여부, 현재 세션 여부 등입니다.
  • 범위에는 ChatGPT, Codex, API Platform 세션이 포함될 수 있지만, 타사 앱 세션이나 타사 서비스용 Sign in with ChatGPT 세션은 관리하지 않습니다.
  • 조직 SSO(SAML/OIDC)에 연결된 계정에는 제공되지 않을 수 있고, Codex CLI 세션도 여기서 관리하지 않습니다.

02.6Library — 파일 저장소와 자동 참조

2026년 6월 11일 기준, Library는 Enterprise/Edu/Healthcare 워크스페이스로 배포 중입니다. 사용자가 ChatGPT에 업로드하거나 ChatGPT에서 만든 파일은 Library에 저장되어 나중에 다시 찾아 첨부할 수 있습니다.

  • Library 파일은 워크스페이스 보존 정책을 따르고, 일일 첨부/채팅 한도와 별도의 저장소로 관리됩니다.
  • Owner는 ChatGPT가 답변할 때 Library 파일을 자동으로 참조할지 제어할 수 있습니다. 이 기능을 꺼도 Library 자체, 검색, 열기, 수동 첨부는 막지 않습니다.
  • Healthcare 워크스페이스에서는 Library 자동 참조가 기본 OFF입니다.
  • Library는 새 외부 공유나 다중 사용자 공동 편집 기능을 추가하지 않습니다.
  • Compliance 관리자는 Library 전용 Compliance API endpoint로 Library 파일을 export/delete할 수 있습니다.

02.7Improved memory — 개선된 메모리

2026년 6월 25일 릴리스 노트 기준, Enterprise/Edu에는 개선된 메모리가 배포 중입니다. 메모리가 켜져 있으면 ChatGPT는 수동 저장 메모리만이 아니라 과거 대화의 관련 맥락을 참조해 더 최신의 개인화 응답을 제공할 수 있습니다.

  • 사용자는 메모리 요약을 검토하고, 개인화 응답 아래에서 어떤 메모리·과거 대화·custom instructions가 근거로 쓰였는지 볼 수 있습니다.
  • Enterprise에서는 약 2주간 early access 기간이 있으며, 이 기간에는 관리자가 Workspace settings에서 Use improved memory를 켤 수 있습니다.
  • early access 이후에는 대상 워크스페이스에서 기본 ON이 될 수 있으며, 관리자가 opt out할 수 있습니다.
  • 관리자와 사용자는 legacy Saved memories로 되돌릴 수 있습니다.
  • Codex memory에는 영향이 없습니다. 프로젝트 전용 메모리는 프로젝트 안에만 머물며, 프로젝트 밖 메모리나 대화를 사용하지 않습니다.

Section 03 · ChatGPT

Members — 멤버 / Seat 관리

Workspace settings → Members

초대·삭제·역할 변경·seat 타입 변경이 모두 이 탭에서 일어납니다. Enterprise는 ChatGPT seat과 Codex seat을 자유롭게 섞어서 발급할 수 있고, 한 워크스페이스에 Codex-only seat만 둘 수도 있습니다.

03.1역할(Role) 4종

역할권한 요약
Owner결제·ID 관리·워크스페이스 구성 전체. 다른 Owner를 임명 가능.
Admin일상적인 사용자/그룹 관리. Owner 임명 불가.
Analytics Viewer 신규Member 권한 + Workspace Analytics 읽기 전용. AI 챔피언/팀 리더용.
MemberChatGPT/Codex 일반 사용. 관리 권한 없음.

→ 공식 역할 비교 표

03.2Seat 타입 2종

  • ChatGPT seat — 표준 ChatGPT 인터페이스(채팅·GPT·Apps·캔버스 등) 전체 사용.
  • Codex seat — Codex 사용 환경(App / CLI / IDE / Cloud / Code Review)만 사용. ChatGPT 채팅·메모리·프로젝트 접근 불가.
⚠ seat 변경 주의
ChatGPT seat을 Codex seat으로 바꾸면 해당 사용자의 채팅 기록·메모리·프로젝트(공유 프로젝트 포함)가 화면에서 사라집니다. 데이터가 삭제된 것은 아니며 ChatGPT seat으로 되돌리면 복구됩니다.

03.3주요 작업

  • 초대(Invite member) — 이메일 직접 입력 또는 CSV 업로드(email,role,seat type).
  • 대량 가져오기 — CSV로 한 번에 수백 명 등록 가능(예: user1@co.com,member,Codex).
  • 역할 변경 — Owner만 가능.
  • Seat 변경 — 현재 공식 가이드는 OpenAI 계정 담당자 경유를 안내합니다. 특히 ChatGPT seat → Codex seat 전환 전에는 ChatGPT 데이터 가시성 변화 여부를 먼저 검토해야 합니다.
  • Pending invites/Requests — 보류 중 초대·가입 요청에서도 선택된 seat type을 함께 검토하며 승인/재전송/수정/거절합니다.
  • 멤버 제거 — ··· 메뉴 → Remove member.
  • 기본 seat 타입(Default seat type) 설정 — 이후 신규 가입자(SCIM 포함)는 이 값으로 발급.

Section 04 · ChatGPT

Groups — 그룹

Workspace settings → Groups

그룹은 RBAC(역할 기반 접근 제어)와 GPT/프로젝트 공유의 “단위”입니다. 워크스페이스 안에서 직접 만들거나, IdP의 디렉터리 그룹을 SCIM으로 자동 동기화할 수 있습니다.

  • 그룹 생성·삭제, 멤버 추가/제거
  • 그룹 멤버십 검토
  • SCIM 동기화 그룹은 이름 옆에 SCIM 배지가 표시되어 직접 관리 그룹과 구분
  • 같은 이름의 ChatGPT 그룹이 이미 있으면 별도 중복 그룹을 만들기보다, 그 기존 그룹이 SCIM 관리 그룹으로 전환될 수 있으므로 IdP 쪽 멤버십을 먼저 점검하는 편이 안전합니다.
RBAC 사용 시 필수
역할(권한)은 그룹에 부여합니다. 따라서 RBAC를 쓰려면 그룹이 반드시 필요합니다. 개인 사용자에게 직접 역할을 붙일 수는 없습니다. [SCIM FAQ]
Section 05 · ChatGPT

Permissions & Roles — 핵심 거버넌스 탭

Workspace settings → Permissions & Roles

Enterprise/Edu 관리자에게 가장 중요한 한 화면. 워크스페이스 전체에 적용되는 기본 권한, 그리고 그룹 단위로 더 엄격하거나 더 관대한 Custom Role을 만드는 곳입니다.

05.1Default permissions(기본 권한)

Custom Role이 없는 사용자에게 적용되는 워크스페이스 기본값입니다. 스크롤하며 토글로 기능별 ON/OFF를 결정합니다.

유의
Custom Role을 가진 사용자에게는 Default가 적용되지 않습니다. “전 직원에게 켜두고 싶은 기능”도 Custom Role 안에 다시 명시해야 합니다. [RBAC 가이드]

RBAC는 개인에게 직접 부여하는 방식이 아니라 그룹 기반입니다. Groups 탭에서 그룹을 만들거나 SCIM으로 동기화한 뒤, 해당 그룹에 Custom Role을 할당해야 합니다.

05.2Custom Roles — 토글 가능한 권한 카테고리

각 Custom Role 안에서 다음 항목을 개별 ON/OFF 할 수 있습니다(최신 공식 RBAC 기준).

  • Canvas — 캔버스 코드 실행 / 네트워크 접근 기본값
  • ChatGPT agent — 에이전트 모드(웹 자동 조작) 사용
  • Codex — Codex 사용 및 인터넷 접근 관련 제어(아래 Codex 섹션 참조)
  • Apps — 앱 사용 허용 여부, 앱별 선택, action 단위 제어
  • GPTs — 생성·편집·공유 범위(invite-only / workspace / public), 서드파티 GPT 접근
  • Projects — 프로젝트 생성·편집 권한
  • Record — 과거 노트·녹취/기록 참조 권한
  • Search — 웹 검색, 에이전트 검색
  • Shared projects — 공유 프로젝트 참여
  • Skills — Skill 생성·사용, skill 파일 업로드, 공유, 워크스페이스 게시, 다른 멤버용 설치
  • Link sharing — 대화 링크 공유 범위
  • Available models — 이 Role이 쓸 수 있는 모델 한정
  • Usage limits / Spend controls — 크레딧/메시지 한도(아래 참고)

여러 Custom Role을 동시에 가진 사용자는 합집합(가장 관대한 권한)으로 해석됩니다.

참고로 Apps는 앱 단위 접근은 제어할 수 있지만, 앱 UI 자체를 개별로 숨기는 방식은 아닙니다.

Lockdown Mode 역할
Lockdown Mode를 지원하는 워크스페이스에서는 이를 단일 토글이 아니라 역할 수준 보안 구성으로 다룹니다. 해당 역할을 받은 멤버는 live web search, deep research, agent mode, Canvas 네트워크, 일부 앱/MCP/connector 동작이 제한될 수 있으므로, 할당 전 각 앱과 action, 원본 시스템 권한을 함께 확인해야 합니다.

05.3Spend controls (Usage limits / overages)

Enterprise는 계약 단위 shared credit pool을 사용하며, 모든 사용자와 seat type이 고급 기능 사용 시 이 pool에서 차감됩니다. 공식 Usage limits 문서는 이제 사용자별 월간 한도와 워크스페이스 overage limit을 별도 제어로 설명합니다. Usage limits는 Workspace settings에서, overage limit과 usage alert는 Global Admin Console의 Billing에서 관리합니다. [Flexible pricing]

  • Usage limits: Workspace settings → Usage limits에서 월간 workspace 기본값, group 기본값, user override를 설정합니다.
  • 적용 순서: user override → 사용자가 속한 그룹 중 가장 높은 group limit → workspace default 순으로 적용됩니다.
  • 증액 요청: 사용자가 한도 초과 시 increase request를 보낼 수 있고, 관리자는 Usage limits → Pending Requests에서 승인/거절합니다. 승인된 값은 일회성 임시 해제가 아니라 user override로 남습니다.
  • 기존 주간 제한과의 관계: 새 Usage limits를 아직 설정하지 않았다면 기존 Permissions & Roles → Weekly limits가 fallback으로 계속 적용됩니다.
  • 마이그레이션 일정: 남아 있는 주간 제한은 2026년 8월 초 월간 workspace/group 기본값으로 자동 마이그레이션될 예정입니다. 이후 weekly limit 설정은 더 이상 적용되지 않습니다.
  • Overage limit: shared credit pool이 먼저 소진되면 Global Admin Console → Billing의 workspace overage limit이 추가 사용 가능 범위를 결정합니다. user usage limit은 overage 사용 중에도 계속 적용됩니다.
  • No limit 의미 차이: Usage limits의 group override에서 No limit은 workspace default 상속을 뜻하지만, Billing의 workspace overage limit에서 No limit은 overage cap이 설정되지 않았다는 뜻입니다.
  • Usage alerts: credit threshold, committed credits 소진, overage limit 도달 시 알림을 보낼 수 있지만 사용을 차단하지는 않습니다. 차단이 필요하면 overage limit을 설정합니다.
  • 운영 패턴: 엔지니어링/AI 챔피언 그룹은 넉넉한 group default, 일반 사용자 그룹은 보수적 default, 예외 사용자는 user override로 관리하는 편이 명확합니다.
  • 관찰 위치: 한도 설정은 Usage limits, overage와 unbilled usage는 Billing, 실제 소비 추세와 원인 분석은 Workspace Analytics / Billing / Codex Analytics를 함께 봅니다.

→ Apps admin controls 공식 가이드

08.1워크스페이스 단위 설정

  • Enterprise/Edu는 모든 앱이 기본 OFF — Owner가 켜야 사용 가능
  • 앱별로 활성/비활성 토글
  • 활성화 시 admin은 어떤 Custom Role에게 노출할지 즉시 지정
  • 앱이 action 단위 제어를 지원하면 action별 검토·차단 가능
  • Action control은 모두 허용 / 읽기만 허용 / 커스텀 선택을 지원하고, 이후 새 action이 추가될 때도 자동 허용 / 새 read action만 허용 / 새 action 기본 차단 정책을 고를 수 있음
  • App permissions는 ChatGPT가 앱을 사용하기 전에 언제 사용자에게 묻는지 정하는 설정이며, 지원되는 앱에서는 기존 action confirmation을 대체합니다.
  • App template: Enterprise/Edu Owner/Admin은 GitHub Enterprise, Snowflake, Databricks용 workspace-specific app template를 사용해 초안 앱을 만든 뒤, 게시 후 동일하게 role access, action controls, app permissions를 Apps 화면에서 운영

RBAC는 누가 앱을 쓸 수 있는지, Action control은 그 앱이 무엇을 할 수 있는지, App permissions는 ChatGPT가 언제 사용자 확인을 요청하는지를 다룹니다. App permissions 옵션은 배포 상태와 앱별 지원 여부에 따라 Always ask, Any changes, Important actions, Never ask 등으로 보일 수 있습니다.

08.2Sync(인덱싱) 설정

  • Google Drive, SharePoint, GitHub 등은 사전 인덱싱(synced connector) 지원 — 응답 품질↑, 속도↑
  • 특정 Shared Drive/폴더만 허용, 특정 파일 형식 제외

  • Google Workspace 관리자는 신규 action scope에 맞춰 Drive/Docs/Sheets/Slides 재승인이 필요할 수 있음
  • Google Drive sync 버전과 non-sync 버전은 현재 서로 다른 권한으로 분리 제어 불가
  • 두 가지 셋업 방식:
    • Quick setup — 사용자가 자기 계정으로 인증
    • Admin-controlled access — 관리자가 중앙에서 더 세밀하게 제어

08.5Microsoft 계열 연결 시 주의

Outlook, Teams, SharePoint 연결은 Microsoft Entra ID(구 Azure AD)에서 각 서비스마다 권한 부여가 선행되어야 합니다. 특히 2026년 4월 기준 admin-managed SharePoint sync는 delegated scope에서 Microsoft application scope로 마이그레이션 중이므로, 앱 상단의 Reconnect SharePoint for better syncing 또는 Re-auth required 경로로 재인증이 필요할 수 있습니다. 또한 앱 설정에서 Microsoft Purview sensitivity labels를 구성할 수 있습니다.

  • Owner/Admin이 Workspace settings → Apps에서 Teams를 한 번 연결하고, scope picker로 포함할 Teams 콘텐츠를 선택합니다.
  • 필요하면 Microsoft Purview sensitivity label filter로 동기화 범위를 더 좁힐 수 있습니다.

  • 정기 self-service Microsoft Teams 앱과는 별도이므로, 사용자별 앱 연결 안내와 관리자 관리형 sync 안내를 구분해야 합니다.

최근 Box / Notion / Linear / Dropbox와 Google / Microsoft 계열 앱에도 새 write action이 추가되고 있어, 앱을 켤 때는 scope 승인 + Manage actions 검토 + 필요 시 사용자 재연결을 함께 운영 절차로 잡는 편이 좋습니다. [Release Notes]

Codex Enterprise — 어디서 어떻게 설정하나

Codex(Enterprise)는 ChatGPT Enterprise 워크스페이스 안에 “포함”되는 형태입니다. 따라서 모든 관리 진입점은 동일한 Workspace Settings이며, Codex 전용 화면은 그 안에 별도 섹션으로 존재합니다. Codex는 Local(App/CLI/IDE 확장) 과 Cloud(웹/iOS/Code Review/Slack/Linear) 두 사용 환경으로 나뉘며, 둘은 독립적으로 켜고 끌 수 있습니다.

Codex가 제공하는 Enterprise 보안
  • 고객 데이터로 학습하지 않음
  • App / CLI / IDE는 Zero Data Retention — 코드는 개발자 환경 밖으로 나가지 않음
  • 거주지(Residency)·보존(Retention) 정책은 ChatGPT Enterprise와 동일하게 적용
  • 저장 시 AES-256, 전송 시 TLS 1.2+
  • Compliance API로 모든 사용 기록 감사 가능

Device code authentication for CLI

원격 개발 박스, SSH 서버, 컨테이너 등 비대화형 환경에서 codex CLI에 device code 로그인을 허용할지 토글. 원격/Linux 서버에서 작업하는 팀은 반드시 ON으로 두어야 합니다. 명령어는 OS 무관: codex login --device-auth

Codex access tokens for automation

브라우저 로그인 없이 신뢰된 자동화가 ChatGPT 워크스페이스 ID로 Codex Local을 실행해야 할 때 쓰는 토큰입니다. 일반 OpenAI API 호출이면 Platform API key를 계속 쓰고, Codex 실행이 워크스페이스 권한·감사·사용량에 연결되어야 할 때만 access token을 사용합니다.

  • 관리 토글: Codex Local을 켠 뒤 Allow members to use Codex access tokens를 켭니다.
  • 만료 한도 제어: Owner/Admin은 Workspace Settings → Permissions & roles → Codex Local에서 Access token expiration limit를 정해, 멤버가 선택할 수 있는 최대 만료 기간을 제한할 수 있습니다. 이 제한은 신규 토큰에만 적용됩니다.
  • 좁은 배포: Custom Role을 쓰는 조직은 access token 권한을 필요한 그룹에만 부여합니다.
  • 일회성/비영구 자동화: CODEX_ACCESS_TOKEN 환경변수에 저장하고 codex exec를 실행합니다.
  • 영구 로컬 로그인: printf '%s' "$CODEX_ACCESS_TOKEN" | codex login --with-access-token을 사용합니다.
  • 운영 원칙: secret manager에 저장하고, 로그·티켓·채팅에 노출하지 않으며, 가능하면 7/30/60/90일 같은 유한 만료일을 두고 정기 회전·폐기합니다.

12.6Computer Use / Browser Developer mode

2026년 6월 11일 기준, Codex App은 macOS와 Windows에서 Computer Use를 지원합니다 (출시 시점의 지역 제한: EEA, 영국, 스위스 제외). Windows에서는 Computer Use가 active desktop foreground에서 동작하므로, 사용자가 같은 Windows 세션을 동시에 쓰는 동안 백그라운드 자동화처럼 운영할 수 없습니다.

  • 설치: Codex settings → Computer Use에서 plugin을 설치합니다. macOS는 Screen Recording과 Accessibility 권한이 필요합니다.
  • Record & Replay: macOS에서는 반복 업무를 한번 시연해 재사용 가능한 skill로 만드는 Record & Replay가 추가되었습니다. Computer Use가 켜져 있어야 하고, 조직이 [features].computer_use = false로 막아 두면 함께 비활성화됩니다.
  • Windows 운영: target app을 화면에 보이게 두고, 장시간 작업은 기기를 잠금 해제·인터넷 연결 상태로 유지하거나 VM/원격 제어 조합을 권장합니다.
  • Windows app policy: $CODEX_HOME/computer-use/config.toml의 [apps]에서 allowed/denied 앱을 지정할 수 있고, denied가 allowed보다 우선합니다.
  • 관리자 제어: requirements.toml에서 [features].computer_use = false로 Computer Use 설치·활성화 흐름을 비활성화할 수 있습니다.
  • Browser Developer mode: Browser use에서 CDP 기반 성능 프로파일링, console/network/DOM/style 진단을 허용합니다. 사용자 기본값은 OFF이며, 관리자는 [features].browser_use_full_cdp_access = false로 비활성화할 수 있습니다.
  • 기타 UX: app composer의 /init은 AGENTS.md scaffold를 생성하고, usage-limit 오류는 가능한 경우 워크스페이스 안내와 reset timing을 더 명확히 보여주며, command menu에는 Unread chats 섹션이 추가되었습니다.

공식 Codex 문서의 페이지명은 Remote connections이고, 일부 관리자·릴리즈 노트 표면에서는 Remote Control access라고 표현됩니다. 2026년 6월 25일 기준 Codex Remote는 Enterprise/Edu에서 GA로 제공되며, 같은 계열의 원격 제어 기능이므로 운영 문서에서는 두 용어를 함께 안내하세요.

  • ChatGPT 모바일 앱에서 연결된 Mac/Windows Codex App host를 제어하거나, 다른 지원 Codex App 기기에서 작업을 이어갈 수 있습니다.
  • Windows host는 ChatGPT iOS/Android 또는 Mac의 Codex App에서 제어할 수 있지만, Windows Codex App은 현재 다른 컴퓨터를 제어하는 쪽으로는 사용할 수 없습니다.
  • 원격 연결은 host의 프로젝트, 스레드, 파일, credentials, 권한, 플러그인, 브라우저 설정, 로컬 도구를 그대로 사용합니다.
  • 사용자는 모바일에서 후속 지시, 질문 응답, 실행 방향 전환, command/action 승인, diff·테스트·터미널·스크린샷 확인을 할 수 있습니다.
  • Pairing: Remote Control은 지원 모바일 기기와 host 간 인증된 1:1 QR pairing을 사용합니다. 2026년 6월 8일 이후 사용된 연결은 유지되지만, 오래 비활성 상태였던 연결은 다시 pairing해야 할 수 있습니다.
  • Sign-out 동작: 로그아웃하면 Remote Control은 꺼지지만 기존 pairing 자체를 제거하지는 않습니다.
  • 모바일 설정은 Codex App에서 시작하며, CLI나 IDE Extension만으로는 설정할 수 없습니다.
  • DigitalOcean Droplet Workspace plugin: 대상 Enterprise/Edu 사용자는 DigitalOcean Droplet을 만들고 SSH 접근을 구성해 Codex App의 remote workspace로 연결할 수 있습니다. 연결 전 ChatGPT 모바일 앱과 Codex App을 최신 버전으로 업데이트해야 합니다.
  • Windows에서 Computer Use를 함께 쓰는 작업은 foreground 세션이 필요하므로 host를 잠금 해제 상태로 유지하고 해당 데스크톱을 작업에 전용하는 편이 안전합니다.
  • 워크스페이스 환경에서는 admin이 Remote Control access를 켜야 할 수 있고, SSO/MFA/passkey 절차가 추가될 수 있습니다.

Codex Policies — 클라우드 관리 requirements.toml

chatgpt.com/codex/settings/policies

개발자 노트북에 디바이스 파일을 직접 뿌리지 않고도, 그룹별로 다른 Codex 로컬 제약을 적용할 수 있는 화면입니다. 여기서 만든 정책은 사용자가 ChatGPT로 Codex에 로그인하는 순간 App / CLI / IDE 모두에 자동 동기화됩니다.

14.1제어 가능한 항목

  • allowed_approval_policies — untrusted, on-request 등 승인 모드 허용 목록
  • allowed_approvals_reviewers / guardian_policy_config — 자동 검토자 허용 여부와 테넌트별 자동 검토 정책 조정
  • allowed_sandbox_modes — 레거시 배포용 sandbox mode 허용 목록. Codex 0.138.0+에서는 가능하면 permission profile 기반 정책으로 옮기는 편이 맞습니다.
  • allowed_permission_profiles / default_permissions — 0.138.0+ 기준 권장 방식. :read-only, :workspace 같은 built-in 또는 조직 정의 custom profile의 허용 목록과 기본값을 중앙 제어합니다.
  • [[remote_sandbox_config]] — 호스트 패턴별 샌드박스 요구사항 오버라이드
  • allowed_web_search_modes — disabled / cached / live
  • [permissions.filesystem].deny_read — 정확한 경로 또는 glob 패턴 기준 읽기 차단
  • MCP 서버 허용 목록 — 어떤 MCP 서버만 허용할지 이름·identity로 매칭. 빈 배열이면 전 MCP 차단
  • Managed hooks — [hooks]와 관리형 스크립트 디렉터리로 lifecycle hook 강제
  • Restrictive command rules — rm, git push 같은 위험 명령에 prompt/forbidden 적용
  • allow_remote_control = false — mobile/다른 기기에서 host를 제어하는 Remote Control access를 관리형으로 차단
  • allow_appshots = false — Appshots를 관리형으로 차단
  • Browser Use, in-app browser, Computer Use 등 특정 사용 환경 비활성화
  • Browser Developer mode의 full CDP access를 금지하려면 [features].browser_use_full_cdp_access = false로 고정
  • Windows/macOS Computer Use 자체를 금지하려면 [features].computer_use = false로 고정
  • 대상 Enterprise 워크스페이스에서 기본 제공되는 plugin sharing을 조직 정책상 꺼야 할 때 MDM 또는 cloud-managed requirements로 비활성화

14.2예시 정책

default_permissions      = ":workspace"
allowed_approval_policies = ["on-request"]
allowed_web_search_modes  = ["disabled", "cached"]

[allowed_permission_profiles]
":read-only" = true
":workspace" = true
# ":danger-full-access" is omitted, so it stays denied.

[rules]
prefix_rules = [
  { pattern = [{ token = "rm" }], decision = "forbidden",
    justification = "Use git clean -fd instead." },
  { pattern = [{ token = "git" }, { any_of = ["push", "commit"] }],
    decision = "prompt",
    justification = "Require review before mutating remote history." },
]

14.3그룹 할당 & 폴백

  • 각 정책을 특정 사용자 그룹에 할당
  • 매칭되지 않는 사용자용 기본(default fallback) 정책 별도 지정
  • 여러 그룹 룰에 매칭되면 맨 처음 매칭된 룰만 적용 — 누락 필드를 다음 룰이 채우지 않음
  • 각 정책은 “해당 그룹용 완성형 프로파일”로 작성할 것

14.4Policy lookup — 누구에게 어떤 정책이 적용되는지 확인

Managed Configuration — OS별 완전 가이드

Cloud-managed requirements 외에도 각 사용자 PC에 정책 파일을 직접 배포해 Codex 동작을 강제할 수 있습니다. 이 섹션의 핵심은 OS마다 적용 방식·경로·한계가 모두 다르다는 점이며, 잘못 설계하면 정책이 강제되지 않거나 사용자가 우회할 수 있습니다.

→ Codex Managed Configuration 공식 가이드

15.1적용 우선순위 (3단계)

같은 항목을 여러 곳에서 정의하면 위쪽이 아래쪽을 덮어씁니다.

  1. Cloud-managed requirements — ChatGPT 웹의 Codex Policies 페이지. 사용자가 ChatGPT 로그인 시 자동 동기화. OS와 무관하게 적용되며 사용자가 우회 불가. ✅ 권장 1순위
  2. OS 레벨 관리형 설정 — macOS는 MDM, Windows는 %ProgramData%\OpenAI\Codex\requirements.toml, Linux는 /etc/codex/
  3. 사용자 개인 설정 — ~/.codex/config.toml. 사용자가 자유롭게 수정
0.138.0+ 권장 기준
최신 공식 문서는 Codex 0.138.0 이상에서 allowed_sandbox_modes보다 permission profile 방식(allowed_permission_profiles + default_permissions)을 우선 권장합니다. 구버전 클라이언트(0.137.x 이하)는 이 키들을 무시할 수 있으므로, fleet 업그레이드 상태를 먼저 확인해야 합니다.

기본값 권장
  • 대부분 사용자 → workspace-write + on-request 승인
  • danger-full-access는 통제된 컨테이너용으로만

  • log_user_prompt = false 유지 — 정책상 필요할 때만 ON
  • 로컬 config.toml과 관리형 정책의 diff를 주기 점검
  • OS별 차이를 인지하고, Windows는 반드시 Cloud-managed requirements와 병행

  • 환경 변수는 전체 작업 동안 유지되지만, secret은 setup script에만 주입되고 에이전트 단계 전에 제거
  • 컨테이너 캐시는 최대 12시간 유지되며, setup script·maintenance script·환경 변수·secret이 바뀌면 자동 무효화

20.4④ Compliance API audit

Compliance API는 워크스페이스의 감사·컴플라이언스 데이터를 SIEM, 데이터 레이크, eDiscovery, DLP 도구로 가져오는 채널입니다. OpenAI Help 문서 기준 Compliance Logs Platform의 보존 기간은 30일이므로, 더 긴 보존이 필요하면 모든 로그를 지속적으로 다운로드해 고객 보존 정책에 맞춰 저장해야 합니다.

2026년 6월 5일 이후 기준 Compliance Platform 문서는 2026년 3월 5일 새 conversation logs 시스템이 릴리스되었고, 기존 stateful route는 2026년 6월 5일 제거 예정이라고 안내했습니다. 현재 날짜 기준으로는 해당 제거일이 지났으므로, 기존 연동이 stateful route에 의존하지 않고 새 logs system 기준으로 마이그레이션되었는지 확인해야 합니다.

→ OpenAI Compliance Platform 공식 가이드 

curl -L -H "Authorization: Bearer YOUR_COMPLIANCE_API_KEY" \
  "https://api.chatgpt.com/v1/compliance/workspaces/WORKSPACE_ID/logs?event_type=CODEX_LOG&after=2026-03-01T00:00:00Z"

주요 엔드포인트: /logs · /codex_tasks · /codex_environments

20.5Compliance API와 Platform Audit Log API 구분

운영 구분 Compliance API는 ChatGPT 워크스페이스의 사용자 활동, Codex, 인증, 감사 로그를 다루고, Admin/Audit Log API는 API Platform 조직의 API 키 생성, 프로젝트 관리, 멤버 변경 같은 관리 이벤트를 다룹니다. ChatGPT Enterprise와 API Platform을 함께 운영하는 조직은 두 로그 체계를 각각의 목적에 맞게 관리합니다.
